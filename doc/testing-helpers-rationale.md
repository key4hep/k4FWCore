# Test helpers for k4FWCore and downstream projects: design rationale

This note explains the design of the test helpers in `cmake/k4FWCoreTesting.cmake`
and why it was chosen over the alternatives. The survey of how ATLAS and LHCb
solve the same problem is in [testing-in-other-experiments.md](testing-in-other-experiments.md).

## What is provided

After `find_package(k4FWCore)`, projects can use two CMake functions.

**`k4fwcore_add_test`** declares any test:

```cmake
k4fwcore_add_test(<name> COMMAND <command> [<arg>...]
                  [WORKING_DIRECTORY <dir> | PRIVATE_WORKING_DIRECTORY]
                  [ENVIRONMENT <var>=<value>...] [LABELS <label>...]
                  [FIXTURES_SETUP <fixture>...] [FIXTURES_REQUIRED <fixture>...]
                  [CHECK_ERROR_MESSAGES] [PROPERTIES <property> <value>...])
```

**`k4fwcore_add_k4run_test`** declares a test that runs a steering file with `k4run`:

```cmake
k4fwcore_add_k4run_test(<name> OPTIONS <options_file> [ARGS <arg>...]
                        [NO_ERROR_CHECK] [<k4fwcore_add_test arguments>...])
```

A downstream project needs nothing more than this:

```cmake
find_package(k4FWCore REQUIRED)
include(CTest)

k4fwcore_add_k4run_test(Simulation OPTIONS options/sim.py ARGS -n 10
                        FIXTURES_SETUP SimFile)
k4fwcore_add_k4run_test(Reconstruction OPTIONS options/rec.py
                        FIXTURES_REQUIRED SimFile)
```

It no longer needs a hand-written `set_test_env` function or an `ENVIRONMENT`
string listing build directories.

## The problem being solved

Before this change, every Key4hep repository wrote its own test environment:
`set_test_env` in k4Gen, k4RecTracker, k4RecCalorimeter and k4ActsTracking, and a
`test_environment` string in k4-project-template and in k4FWCore itself. These
functions list build directories by hand for `LD_LIBRARY_PATH`,
`GAUDI_PLUGIN_PATH` and `PYTHONPATH`. They drift from one repository to the next,
break when the directory layout changes (for example in a superbuild, where
`PROJECT_BINARY_DIR` and `CMAKE_BINARY_DIR` differ), and are only checked by
running the tests.

k4FWCore also had to copy its Python package into a directory generated by
Gaudi (the `copy_directory` target). Otherwise `import k4FWCore` in the build
tree found either the source files or the generated configurables, but not both.

## Design decisions

### 1. Use Gaudi's `run` script instead of writing the environment by hand

Gaudi already generates `${CMAKE_BINARY_DIR}/run` and `<project>env.sh`. They
collect the runtime paths of everything declared with `gaudi_add_module`,
`gaudi_add_library`, `gaudi_add_executable` and `gaudi_install`, on top of the
environment present at configure time. LHCb launches every test through it, and
Gaudi does the same for its own tests.

This is the most important part of the change, and k4FWCore now relies on it for
its own tests:

- `gaudi_install(PYTHON)` is called from the top-level `CMakeLists.txt`. It
  generates a build-tree `k4FWCore/__init__.py` whose `__path__` merges
  `python/k4FWCore` with the configurables in `k4FWCore/genConfDir/k4FWCore`.
  The call has to be at the top level so that the generated package also picks
  up the configurables in `k4FWCore/genConfDir`.
- The `test_environment` block and the `copy_directory` target were removed.
  All the k4FWCore tests pass using only `run`. If `run` misses a path, the
  tests fail, so the environment is now exercised in CI instead of being
  maintained next to it.
- Since `run` comes from Gaudi, it follows Gaudi when it changes its layout, and
  it works the same whether k4FWCore is installed or built in the same tree as
  the downstream project.

`k4FWCoreConfig.cmake` already calls `find_dependency(Gaudi)`, so `run` exists in
every downstream project that finds k4FWCore.

### 2. A keyword-based CMake API instead of a bare command prefix

The first attempt, `fwcore_add_test(name cmd...)`, only prefixed the command with
`run`. Downstream projects can already write `add_test(NAME x COMMAND run ...)`,
so that adds almost nothing. The wrapper is only worth exporting if it covers
what projects actually repeat:

- **`k4run` handling.** The steering file is resolved relative to the source
  directory when it exists there. Otherwise it is resolved relative to the
  working directory, which covers files cloned or produced by earlier tests.
  `k4run` is looked up in `PATH`, so the same call works inside k4FWCore (its
  `scripts/` directory is on `run`'s `PATH`) and downstream.
- **Fixtures, labels and environment** as keywords. Lists such as several
  `FIXTURES_REQUIRED` values are passed as plain CMake lists, without the
  `"\\\\;"` escaping that the old k4FWCore helper needed.
- **Every test gets the label `${PROJECT_NAME}`**, so `ctest -L <project>` works
  in a superbuild.
- **The helpers do nothing when `BUILD_TESTING` is false**, and executable
  targets given as the command are resolved to their path.

The functions carry the package prefix (`k4fwcore_`), like `gaudi_` and
`atlas_`. The local k4FWCore helper `add_test_fwcore` is kept as a thin adapter
so that the list of k4FWCore tests did not need to be rewritten.

### 3. Fail on ERROR and FATAL messages by default for k4run tests

ATLAS catches `ERROR` and `FATAL` lines in every test through `post.sh` or
`noerror.sh`. GaudiTesting does the same through `test_count_messages`, which by
default allows no `ERROR` or `FATAL` messages. A Gaudi job can print an `ERROR`
and still exit with 0, so a check based only on the exit code misses real
problems.

`k4fwcore_add_k4run_test` therefore sets `FAIL_REGULAR_EXPRESSION` to
`K4FWCORE_TEST_ERROR_REGEX` (default `" (ERROR|FATAL) "`, matching Gaudi's
message format). A test opts out with `NO_ERROR_CHECK`. For `k4fwcore_add_test`
the check is opt-in with `CHECK_ERROR_MESSAGES`, because its commands are
arbitrary programs whose output format is unknown.

When this was enabled, six k4FWCore tests failed. All six deliberately trigger
an error and match it with `PASS_REGULAR_EXPRESSION`:

- `TestUniqueIDGenSvcRepeated`
- `FunctionalMetadataThrow`
- `FunctionalMetadataEventLoop`
- `TypeMisMatchDemo`
- `TypeMisMatchDemoMultiple`
- `InvalidOutputCommandsNoCrash`

They are marked `NO_ERROR_CHECK` explicitly. The alternative of disabling the
check automatically whenever a pass regex is set was rejected: it is hidden
behaviour, and it would silently turn the check off for tests that match on
normal output. The test `TestHelperErrorCheck` checks that a command printing an
`ERROR` line and exiting with 0 is reported as failed.

### 4. Shared working directory by default, private on request

ATLAS runs tests in a shared `unitTestRun/` directory and offers
`PRIVATE_WORKING_DIRECTORY`. The same default is used here. Many existing test
chains pass files through the working directory (a producer writes a file, the
next test reads it), and a private directory by default would break all of
them. `PRIVATE_WORKING_DIRECTORY` runs a test in
`${CMAKE_CURRENT_BINARY_DIR}/<name>.dir` for tests whose outputs would otherwise
clash with others.

### 5. `ENVIRONMENT` goes through CTest, before `run`

Extra variables are set with CTest's `ENVIRONMENT` property, which applies
before `run` sources `env.sh`. Variables that `env.sh` does not touch (for
example `K4GEN=...`) keep their value exactly. Path-like variables keep the
user's entries, but after the build-tree paths, which is usually what is
wanted: build-tree plugins must shadow installed ones. Setting the variables
after `run` (`run env K=V cmd`) would let a user accidentally hide the build
tree, for example by writing `PYTHONPATH=/x:$ENV{PYTHONPATH}` with the
configure-time value.

### 6. Test names are not prefixed

Gaudi and ATLAS prefix test names with the package name. Here names are kept as
given, so existing `ctest -R` patterns, `set_tests_properties` calls and fixture
dependencies in k4FWCore and downstream keep working. The `${PROJECT_NAME}`
label provides the grouping instead.

## What was not done (yet)

- **A pytest layer based on GaudiTesting** (`gaudi_add_pytest` plus a
  `K4RunTest(GaudiExeTest)` class with podio/EDM4hep-aware checks: collections
  present, number of events, metadata). This is the LHCb model and the natural
  next step for tests that need more than an exit code and a regex, replacing
  ad-hoc scripts such as `scripts/CheckOutputFiles.py`. It needs pytest in the
  Key4hep stack and a separate discussion about reference files, so it is left
  out of this change. The CMake helpers do not prevent adding it later.
- **Reference-file comparison** in the style of ATLAS `.ref` files or LHCb YAML
  references. Both experiments spend significant effort keeping references up
  to date (big ignore lists, update bots). Structured checks on the output
  files are likely a better fit for Key4hep than diffing logs.
- **Migrating downstream repositories and k4-project-template.** Each
  `set_test_env` can now be replaced by `k4fwcore_add_k4run_test`. This should
  be done repository by repository once k4FWCore is released with the helpers.

## Alternatives considered

| Option | Why not chosen |
|---|---|
| Export only a `run` prefix (`fwcore_add_test`) | Adds almost nothing over `add_test(... COMMAND run ...)`, keeps the per-repository boilerplate, and k4FWCore itself kept its own environment |
| Keep exporting a hand-written environment | This is the status quo that drifts between repositories and breaks in superbuilds |
| ATLAS-style `atlas_add_test` with pre/post scripts and log diffs | Needs a separate framework of bash scripts, and log references are brittle |
| Go straight to pytest/GaudiTesting for everything | A larger change that needs pytest in the stack; most Key4hep tests are "run k4run and check it succeeds", which the CMake helpers cover. Can be added on top |
